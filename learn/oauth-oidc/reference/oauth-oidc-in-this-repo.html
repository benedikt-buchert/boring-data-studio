OAuth and OIDC in this repo

Three connections. Each one uses OAuth, OIDC, or neither. Key card = access token (OAuth). Badge = ID token (OIDC).

ConnectionUsesWhat happens
① Viewer → connectorOAuthViewer allows the script limited access on Google's consent screen.
② Connector → API (A-3)OIDCGoogle's badge for the connector is shown at the API. The shortcut.
② Connector → API (A-5)OAuth + OIDC loginEntra checks the person, then issues a key card made for the BSL API.
③ API → warehouseNeitherThe API logs in as itself: IAM role, Managed Identity or service account.

A-3: the badge as a key

sequenceDiagram
    actor V as Viewer
    participant G as Google
    participant C as Connector
    participant API as BSL API
    V->>G: Consent once (scopes incl. openid)
    C->>G: getIdentityToken()
    G-->>C: Badge: viewer@company.com, aud = connector
    C->>API: POST /data + badge
    API->>API: Signed by Google? aud = our connector? domain allowed?
    API-->>C: Data

Works in v1 because only our connector exists. In a shared gallery connector every API trusts the same audience, so a badge can be replayed (O-13).

A-5: a key card for the API

sequenceDiagram
    actor V as Viewer
    participant C as Connector
    participant E as Entra ID
    participant API as BSL API
    C->>E: Send viewer to login (code flow + PKCE)
    V->>E: Log in (OIDC: who is this?)
    E-->>C: Key card: aud = api://bsl, user claims inside
    C->>API: POST /data + key card
    API->>API: Issued by Entra? aud = me? read user claims
    API-->>C: Data
Same card, different readerThe connector carries the access token but does not read it. The API is the card's intended reader (its audience), so it may read the user claims inside.

③ and CI: machines with identities

sequenceDiagram
    participant J as GitHub Actions job
    participant GH as GitHub OIDC provider
    participant STS as Google Workload Identity Federation
    participant GCP as Google Cloud API
    J->>GH: Ask for an ID token
    GH-->>J: Badge: sub = repo:my-org/my-repo:ref:refs/heads/main
    J->>STS: Swap badge for a key card
    STS->>STS: Rule: repo == my-org/my-repo? (identity)
    STS-->>J: Short-lived Google access token
    J->>GCP: Deploy with the key card
    GCP->>GCP: IAM: may this identity deploy? (permission)

Identity and permission are two steps: the badge says who; IAM decides what. Sources: GitHub Docs, Google Cloud docs.
