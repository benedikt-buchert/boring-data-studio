Lesson 1

Who is this token for?

One question cuts through most auth grillings. For any token on the table, ask: who issued it, whose identity does it carry, and who is allowed to accept it. By the end of this page you can answer all three for every token in the boring-data-studio design.

Four roles

OAuth 2.0 names four partiesRFC 6749 §1.1. Every flow is a conversation between them. Map them to our design once and the rest gets easier.

RoleJobIn our design (A-5, Entra)
Resource ownerThe person whose data or access it isThe report viewer
ClientThe app that wants to call an APIThe connector
Authorization serverLogs the person in and issues tokensEntra ID (or Google, Okta)
Resource serverThe API that accepts tokensThe BSL API

Note what is missing: the warehouse. The BSL API calls the warehouse with its own identity. That is a second, separate conversation, and it gets its own lesson.

Two tokens, two audiences

OAuth gives the client an access token: a key that lets the client call an API. OAuth itself does not even define what an access token looks like; it can be an opaque random stringRFC 6749 §1.4. When it is a JWT, its audience is the APIRFC 9068 §2.2.

OpenID Connect adds an ID token on top: a signed statement telling the client who the user is. Its audience must be the client itselfOIDC Core §2. It is a login receipt for the app, not a key for an API.

The audience ruleAn API accepts a token only when the token's aud names that API. A valid signature is not enough. Current OAuth security practice asks for audience-restricted tokens for exactly this reasonRFC 9700 §4.10.2.

Read a token in ten seconds

A JWT is three base64 parts: header, payload, signature. The payload holds claimsRFC 7519 §4.1. Four of them answer our question:

{
  "iss": "https://accounts.google.com",              // who issued it
  "aud": "1234-abc.apps.googleusercontent.com",   // who may accept it
  "sub": "110169484474386276334",                  // whose identity (stable ID)
  "email": "viewer@company.com",
  "exp": 1763215200                                // when it stops working
}

An illustrative Google ID token payload, the kind the connector gets from getIdentityToken() in option A-3. Values are made up.

Back to the grilling

Now look at the two v1 options again with the audience rule in hand.

  • A-3 sends a Google ID token to the API. Its aud is the connector's client ID, not the API. We use a login receipt as an API key. It works in v1 because our API accepts exactly one audience: our own connector. In a shared gallery connector, every organisation's API would accept that same audience, so one API could replay the token at another. That is O-13.
  • A-5 gets an access token from Entra with aud set to the BSL API (for example api://bsl). Only the BSL API accepts it. That is the textbook shape.

Check yourself

1. Which token exists to tell the app who the user is?

The ID token is OIDC's addition: a signed statement about the user, addressed to the client. Access tokens are for calling APIs.

2. Your API receives a correctly signed JWT whose aud is some other app's client ID. What should it do?

The signature only proves who issued it. The audience says who it was meant for. A token for someone else is never yours to accept.

3. In OAuth terms, which role does the BSL API play?

The API holds the protected resource and accepts access tokens. The connector is the client that calls it.

4. Why can a malicious API replay an A-3 token from a shared gallery connector?

The token's audience is the shared connector. Every API that trusts that audience accepts it, so a token sent to one works at the others until it expires.

5. Which claim names who issued the token?

iss is the issuer, aud the audience, sub the subject (the user's stable ID), exp the expiry.

Say it without looking

Explain OAuth vs OIDC in two sentences.
OAuth gives an app an access token so it can call an API on someone's behalf. OIDC adds an ID token that tells the app who the user is.
A colleague says "the token is signed by Google, so the API can trust it." What do you ask?
"Who is the audience?" A signed token is only for the party named in aud.
